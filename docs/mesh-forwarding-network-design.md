# 节点转发网(mesh)L4 代理链设计

- 日期:2026-11-07
- 状态:设计已确认,待实施计划
- 前置讨论:离线设备自身流量出口(egress)问题;本设计是其组网形态的超集解法,关系见「开放项」

## 1. 背景与动机

项目会部署在不能访问公网的设备上。现状:

- 登录/扫码/激活/刷新、用量查询、软件更新等**自身流量**全部裸 `http.Client` 直连;
- **AI 流量**走回环 :56432 → aliang 隧道 → 平台中继,隧道本身裸 `net.Dialer` 直连;
- 已有 `customer.proxy`(socks5/http)只作用于**过闸的客户流量**(proxy_rules 路由层),完全不覆盖上述自身流量。

离线设备上登录、用量、更新全瘫,隧道一死手机与 AI run 跟着瘫。

本次需求不是「给自身流量配代理出口」,而是**组网**:流量在转发出去之前增加一层判断——是否转发到我们自己的其他节点;其他节点收到后做同样判断,形成逐跳转发网络(形似 Tailscale,形态为 L4 代理链)。

## 3. 数据面架构

### 3.1 数据面载体(实施期修正版)

- **帧协议(两端一致)**:复刻 `app/tunnel/bridge.go` 的 `tcpRouteHeader` 风格——首行 JSON 头 + 原始字节双向转发。字段:来源 device_id、流量类别、目标(host:port / 裸域名 / `dns:`)、path vector、跳数。
- **载体 A(中继)**:**不自建流复用**——piko 客户端每条拨号即一个桥接流(yamux 由 piko 持有,A 侧零 mux 代码)。A 拨 piko 端点 `<B_deviceID>.mesh`,B 侧以 `manager.go:328-345` 的第二端点模式常驻 serve(软失败:平台端点白名单未放行则中继载体降级不可用,LAN 不受影响);**仅自身/AI 流量准入**。B 侧对来源 device_id 做 ACL(仅配置中允许的转发方)。
- **载体 B(LAN)**:每条转发连接一条明文 TCP 直连(设备转发规模下无需自建 mux);**全类别流量可达**。
- **LAN 发现(实施期修正)**:peer_lan 现有发现为服务端编排 + 一次性监听,离线不可用、不可复用。新增 **LAN beacon**:UDP 广播 device_id + mesh 监听端口 + 证书指纹,离线可用;手输地址为兜底。
- **LAN 鉴权(实施期修正)**:复用 peer_lan 的「自签证书 + 指纹钉扎」模式(`agent_peer_lan.go:130-155`、`:349-361`),改为**常驻监听口**;接入受 §8 门禁控制。

### 3.2 转发帧格式

帧头字段:

- 目标:host:port,或裸域名(域名直转/代解析场景)
- 流量类别:自身 / AI / 自定义
- path vector:已访节点 device_id 列表(每跳追加自己)
- 跳数计数

### 3.3 B 侧接收语义(核心)

B 收到转发流后,**把 stream 包成 net.Conn 注入自己的入站管线**,与 56432 等本地监听口进来的流量同待遇:

> 规则匹配 → 队列消费/直发 → 组网再判断(可多跳)→ 本机转发逻辑

由此:

- 末跳出口语义(B 直连 / B 自己的 customer.proxy)零新设计;
- 多跳(A→B→C)免费获得;
- 外壳复用现有协议信封(隧道/peer 同族格式),内部为原始 TCP 流。

**失败语义(定死):mesh 层失败一律错误回源,仅由发起节点(链头)的规则失败策略执行。** 下一跳不可达、环路、通道中断等 mesh 层失败沿 stream 向上传回,中间节点**不就地回落**——否则「回落 direct」会从中间节点的网络位置出去,违背发起方预期且审计混乱。B 的规则若再指向 C 而 C 失败,同样向上冒泡给 A。

### 3.4 出口类型扩展

- outbound 注册表新增 `mesh` 出口类型(与 direct/aliang/socks/http 并列);
- 规则引擎目标类型新增 `forward_to_node`(引用 device_id,平台台账现成);
- 目标节点 = 自己在配置校验期直接拒绝。

## 4. 流量三级分类

| 类别 | 识别方式(均为现成机制,不猜流量) | mesh 载体准入 |
|---|---|---|
| 自身流量 | egress 发起点在代码中显式(登录/用量/更新) | LAN + 中继 |
| AI 流量 | `shouldForceAliangRoute`(回环 :56432)已识别 | LAN + 中继 |
| 用户自定义流量 | 其余全部(TUN/代理端口入站) | **仅 LAN** |

依据:平台中继是自有带宽,不承载任意用户流量(带宽滥用 + 审计风险);用户自定义流量的 mesh 主诉求本就是局域网场景(离线设备与出口节点同网段)。跨网段的用户流量回落本地正常出口。

## 5. 中继载体的流复用接入

现有 WS 隧道承载控制面消息与 peer-link 载荷。增加流复用通道:

- 中继载体 = A 拨 piko 端点 `<B_deviceID>.mesh`(复用既有桥协议模式,兼容旧版节点——平台端点白名单未放行则中继载体退化为不可用,LAN 载体不受影响);
- 自身/AI 流量经 mesh 出口时优先 LAN(同网段直连更快),LAN 不可达再走中继载体;
- 用户自定义流量禁止走中继载体(引擎层硬约束,不依赖前端);
- 中继载体上平台是字节搬运方:**平台不解析数据面**。

## 6. DNS 三层设计

缺陷来源:规则按 IP 匹配 + 流量只有域名时,A 必须先解析才能匹配,离线解析失败 → 流量永远到不了转发判断;更深层:TUN 路径上应用在内核里先做 DNS,解析失败连 TCP 都不发起,域名直转没有触发机会。

**层 1(地基):DNS 走 mesh 代转发**

- TUN 的 UDP/53 处理已存在且已用 miekg/dns 解析查询(`inbound/tun/tunnel/udp.go`,现仅记日志),扩展为:命中 DNS 转发规则时不再透传公网 DNS,查询经 mesh stream 发给末跳节点,B 用自己的上游解析后回包;
- A 内核拿到真实 IP → 应用发起 TCP → 规则匹配时 IP/域名信息齐全,任何形式规则可命中;
- 在线/离线行为一致,规则引擎无需双轨语义;
- **DNS 来源归类(定死)**:TUN 元数据只有 IP/端口,无法区分查询来自自身进程还是用户进程。规则:**TUN 上的 DNS 查询一律归自定义类,仅 LAN 载体**——真离线主场景只有 LAN 可用,此归类无损;**自身/AI 流量不依赖 TUN DNS**:它们的 egress 调用点显式持有目标域名,直接以域名直转语义走 mesh(层 2),由末跳解析——因此即便出现「平台可达但内网 DNS 不通」的病态受限拓扑,自身/AI 仍可用,不依赖本地解析。

**层 2(优化):域名直转**

- 代理入站的纯域名流量 + 域名类规则命中 → 不解析、带域名转发,末跳代解析(socks5 remote-DNS 语义),省一次 DNS 往返。

**兜底:解析失败策略**(IP 类规则 + 层 1 也不可用)

- 可配置:拒绝连接 / 回落 direct / 强制转发到指定节点。

## 7. 防环与风暴分析

三层防线:

1. **层 0 配置期**:组网规则是节点间有向图,保存时静态环检测,成环告警/拦截(UI 红牌);目标节点 = 自己校验期拒绝。
2. **层 1 转发期 path vector(主防线)**:帧头带已访节点路径,每跳追加自己的 device_id;节点收到流发现自己已在路径 → 立即拒绝。日志可见完整环路,排障价值大。
3. **层 2 跳数硬顶**:默认 5、上限 8,路径字段异常时的数值保险。

风暴分析:本设计**无任何 1→N 泛洪语义**,每条连接按规则 1:1 转发到单一出口。环的最坏后果是「这条连接多绕几跳后快速失败」:最多消耗跳数上限条 stream,错误回源后连接关闭,资源有界,无放大。DNS 代转发同为单 stream,吃同一套防线。

## 8. 门禁

- 新增「允许被其他节点转发流量」开关,**默认关**;
- 复用 peer-link 设备门禁的既有模式(仪表盘读写 + 内核注册时门控);
- 关闭时其他节点的转发请求被拒,已有连接不受影响(连接级拒绝,非断流);
- **发布门(f85643b 评审追加)**:LAN 载体在证书指纹钉扎落地(Task 9/10)之前,拒绝文案可区分「forward disabled」与「not allowed」——内网任意主机可借此探明门禁状态与 peers 名单。属内网信任模型已接受的风险,但 **mesh 接收能力不应随指纹钉扎之前的版本对外发布**。

## 9. 前端设计(app/website 仪表盘,已确认)

### 9.1 入口与布局

- 侧栏「代理」族下新增「组网」导航项;
- 布局 = **左画布 + 右常驻详情双栏**;顶部「拓扑 / 规则」视图切换;视图切换条旁挂**全局状态条**(绿=平台在线 / 琥珀=平台不可达·兜底生效中,见 §9.4 与 §10)。

### 9.2 画布(在线模式)

- **连线 = 节点对容器**(非单规则):一根线代表一对节点间的转发关系,线上数字徽标显示规则数;点击线,右栏列出该节点对全部规则卡片(增删改、优先级拖拽排序);
- **节点卡片**:状态灯(绿=在线/灰=离线/黄=兜底生效中)、设备名+device_id、子网标签(同网段节点自动标「可直达」)、公网出口能力标签、被依赖计数(删节点前风险评估);点击卡片右栏显示节点详情;
- **环路红牌**:拖拽连线成环时画布即时拦截「检测到环路,无法保存」(层 0 的 UI 表现);
- 在线数据来源:平台聚合各节点上报——在线状态(台账)、子网/LAN 网段、互相可达性(peer_lan 发现 + 心跳)、**公网出口能力(节点自报字段)**。平台只做汇聚展示与配置下发,不解析数据面。

### 9.3 规则卡片字段

- 流量类别(色点):自身 / AI / 自定义;
- 命中条件:域名 glob / IP 段 CIDR / 端口 / DNS 全部;
- 动作:带 IP 直转 / 域名直转(末跳代解析)/ DNS 代转发;
- 失败策略:回落 direct / 拒绝连接 / 转指定节点;
- 优先级:拖拽排序,规则间短路匹配。

### 9.4 离线兜底(预配置模式,常驻卡片)

- 画布下方常驻「离线兜底」配置卡片,**在线时即可配置**:
  - 兜底节点:手动输入 LAN 地址(IP:port,该地址即 peer_lan 广告的 mesh 监听口),或从 peer_lan 发现的候选列表点选;
  - 勾选离线时哪些流量类别走兜底(AI / 自身 / 自定义);
- **兜底语义(定死:兜底式,非覆盖式)**:兜底是 mesh 出口内部的**最后失败分支**——该类别仅当无可用正常 mesh 路径(LAN 与中继均不可达或转发失败)时才落兜底节点;LAN 规则仍可达且更优时,不会被手输兜底地址覆盖。兜底执行位置在规则失败策略**之前**(兜底也失败才走失败策略);**兜底仅由发起节点(链头)的 mesh 出口执行,与失败策略同位;中间跳不落兜底**(否则重现 §3.3 要防止的「流量从中间节点位置出去」问题);
- 设备真离线 → 兜底在流量实际需要时生效,顶部状态条变琥珀色「平台不可达 · 兜底生效中」;恢复在线自动失效;
- 零到场配置;仪表盘本身走 LAN 本地访问,离线时页面照常打开;
- 离线时页面上 LAN 发现的候选节点照常可点选(peer_lan 不依赖平台)。

### 9.5 二期

- 手机端(App)组网界面;自动选路;UDP 转发;限流。

## 10. 错误处理

| 场景 | 行为 |
|---|---|
| 出口节点离线 | mesh 层失败**错误回源**(§3.3);链头先落兜底(若勾选),兜底也失败才执行规则失败策略:回落 direct / 拒绝 / 转指定节点 |
| 环路命中 | path vector 拒绝,错误回源,连接关闭 |
| mesh 通道中断 | 在途转发连接断开、错误回源;链头对**新连接**按「无可用正常路径」判定,先落兜底(若勾选),再走失败策略;中间跳不落兜底 |
| 平台不可达 | 中继载体不可用(LAN 不受影响);状态条提示;流量按兜底式语义落兜底 |
| LAN 发现失败 | 仅剩手动输入兜底地址可用 |
| DNS 上游失败 | 向 A 返回 SERVFAIL,应用按自身重试逻辑处理 |

## 13. 开放项

- **平台协调(中继载体上线前置,三项合并)**:①隧道 token 的端点白名单放行 `<deviceID>.mesh` 端点(B 侧 serve 已随隧道恒接线,白名单未放行时上游 Listen 软失败);②configure 帧下发 `piko_proxy_url`(piko 代理面地址,与现有 `piko_upstream_url` 的上游面是同一 piko server 的两个端口,A 侧拨号走代理面);③两项任一缺失时中继载体自动软失败(agent 侧不报错不重试,`DialPeerMesh` 返回「不可用」错误),LAN 载体不受影响——平台侧完成两项后中继载体即刻可用,无需 agent 发版;
- **与 egress(自身流量出口代理)的关系**:同网段存在出口节点时,mesh LAN 载体即自身流量的出口方案,无需另配代理;纯内网且无同网段节点时,仍缺「自身流量走本地代理出口」能力——此前讨论的 `customer.egress_proxy` 小功能是否立项,待定;
- 中继载体的带宽审计与限流:一期不做,平台侧如出现滥用需有观测手段;
