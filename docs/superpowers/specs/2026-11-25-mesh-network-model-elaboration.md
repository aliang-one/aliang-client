## 0. 你定的原则

1. **公网云端链路永远是兜底。** 组不起来也必须可用。
2. **组网是新增的网络选择，不是替换。** 能组、且允许组的设备都尝试；组上后优先走组网，公网 fallback。
3. **组网主要服务 aliang-peer 和文件传输。** agent 控制和 AI 问答默认仍走公网。
4. **对话直传是设备上的可选项。** 手机能直达时才提供；云端没有这段历史是用户自选。
5. **访问边界。** 同账号设备不论网络环境都能互访；不同账号不能互访。

v0.2 新增两条：

6. **没有公网的内网设备，主动搭桥到一台出口设备。** 搭不上就什么都谈不上。下一跳由用户在内网设备上手选；搭上之后业务流量和 AI 流量自动经下一跳出去。
7. **路径规划不做自动的。** 场景不复杂，手动指定下一跳就够；自动规划只是控制面上的 convenience，意义不大。真正考验的是底层架构。

## 1. 流量分五类，各有默认链路

**设计规则：组网只替换数据路径，不替换协调和记账。** 云端负责协调、记账、兜底。唯一的例外是你明确选择不上云的对话。

| 流量类 | 包含什么 | 默认链路 | 组网后 | 云端留什么 |
|---|---|---|---|---|
| 控制面 | 上线、心跳、会话列表、审批投递、终端 | 云端 | 不变。内网设备经搭桥链路到云端 | 全部 |
| 业务消息流 | AI 问答、插话、运行状态 | 云端 | 仅当设备开了「对话直传」 | 默认全部 |
| 设备互访 | aliang-peer：执行命令、取文件、设备备注 | 云端中继 | 优先通过局域网或尾网直连 | 谁在何时对谁做了什么 |
| 文件传输 | 手机下载上传、设备间互传 | 云端 + 对象存储 | 优先直连，设备间传输保留既有打洞能力 | 传输记录，不含内容 |
| 出口流量 | AI 流量经另一台设备出网 | 不启用；内网设备默认启用 | 用户指定的下一跳 | 委托记录 |

## 2. 能连云的设备：组网怎么形成

1. **上报**：设备经 agent 通道报告——账号身份、是否允许组网、候选地址（网卡地址、尾网地址、出口 IP）、NAT 类型、支持的载体。
2. **协调**：云端为每对设备算一份有序的候选路径表，下发给两端。
3. **探测**：轻量探测，不建连、不发凭据。
4. **核验**：选中的路径上先核对对方身份（mesh 公钥 + host key 指纹钉扎），再发凭据。
5. **选路**：标记当前可用路径。
6. **保活与回退**：路径失效自动回云端，恢复自动切回。
7. **学习**：经云端连上后把对方当前的局域网地址学成候选。

连不上云的设备不走这套，走 §4 的搭桥。

## 3. 一对设备之间的路径，和底层技术

| 序 | 路径 | 什么时候用 | 底层技术 | 身份核验 | 现状 |
|---|---|---|---|---|---|
| 1 | 局域网直连 | 同一局域网或可路由私网 | SSH（mesh-exit 通道到对端 56432） | mesh 公钥 + host key 钉扎 | 可用，是目前唯一在用的；每条流一次 SSH 握手 |
| 2 | 尾网直连 | 两端装了 Tailscale 一类 | 同上，地址换成尾网地址 | 同上 | 没自动化；手填能走 |
| 3 | 跨网打洞直连 | 两端都能访问公网、希望跨 NAT 直连 | QUIC + STUN + 云端信令 | token 门禁 + TLS 指纹钉扎 | D3 已确认冻结 mesh 用途，文件传输独立保留 |
| 4 | 云端中继 | 以上都不通 | 平台托管中继 | 中继票据 + SSH | 接收侧已修；发起侧未通 |
| 5 | 搭桥到出口设备 | 内网设备没有公网，但能在局域网内到达出口设备 | 同路径 1，加「全量出口」模式 | 搭桥审批 + mesh 公钥 | LAN 的 DNS + TCP 转发原语已实现；全量出网、首次审批和入号待打通 |
| 6 | 手机直连设备 | 手机和设备同网 | 明文 + 一次性短票 + 应用层加密 | 短票 + 证书指纹钉扎 | 手机的拨号没接 |

**底层技术三分工**：

- **SSH 留作局域网 / 尾网直连和搭桥的载体。** 安全模型成熟。要改的是「一个节点一条连接、多路复用」，解决每条流一次握手。
- **QUIC 打洞保留在文件传输路径。** Mesh 跨网打洞按 D3 冻结。
- **中继留作兜底。** piko 就是我们的「T3 Connect」。
- 不嵌入 WireGuard overlay（tsnet）；把 Tailscale 当「用户自带的免费跨网直连」。
- 业务代码只看到一个抽象：`Dial(对端, 流量类)` 返回一条已核验身份的连接；选路、回退、记账在里面做。

**D3 已确认**采用乙′。设备间保留局域网、尾网和平台中继，尾网使用设备已有的可达路径。

## 4. 没有公网的设备怎么加入

### 有出网、没入站的（在 NAT 后面）

设备本来就能连云端，已经在账号的设备列表里，只是别人连不进来。跨网直连使用可达尾网，直连不可用时由平台中继兜底。T3 Connect 对应平台中继，Tailscale Serve 对应尾网地址。

### 完全没有互联网的：搭桥到出口设备（你定的场景）

首先由 C 在局域网可达范围内选一台能出网的 B。C 到 B 使用已实现的 LAN `mesh-exit`，B 负责对外出网。C 无需能访问公网或打洞信令服务。第一跳必须有可用的局域网路径。平台中继属于两端已经能接入平台时的跨网路径。

**第一步：搭桥**

1. 内网设备 C 打开「下一跳」页，看到可达的出口设备列表：局域网发现的，加上手输地址添加的。
2. 你选中 B，点「搭桥」。C 向 B 发搭桥请求，带上：自己的设备 ID、组网公钥、名称、申请的权限（经你出网 / 互访），以及一个证明持有私钥的签名。
3. B 批准：
   - C 已经是同账号下的已知设备 → 自动批准；
   - 否则 → B 的仪表盘出现一条待批准项。B 已登录、手机 App 存活且能接收事件时，可按现行通知规则提示；用户可在 B 上确认。App 下线期间不推送。
4. 批准后自动做完今天要手做的三件事：B 把 C 的组网公钥写进自己的授权列表（带权限范围）；C 把 B 的 host key 钉进自己的对端配置；B 打开「允许转发」。
5. C 把下一跳设为 B，并进入「全量出口」模式。

**第二步：出网**

C 的域名解析和全部 TCP 连接——agent 到云端的通道、AI 请求、登录、更新——都经搭桥链路交给 B，由 B 按自己的规则决定怎么出网。对 C 来说，B 就是它的网络出口。这就是「业务流量 + AI 流量自动走下一跳」。

**第三步：入号（加入账号并完成注册）**

你问这一步怎么实现。答案是复用现有的扫码登录，只是不用摄像头：

1. C 经 B 向官网发起扫码登录初始化，拿到 device_code 和 scan_code（今天的扫码登录就是这一步，只是把 scan_code 画成了二维码）。
2. C 把 scan_code 经搭桥链路交给 B，B 用自己的登录态转交云端。
3. B 所属账号的手机 App 在线时显示「设备 X 请求加入」，用户确认。App 下线时保留待确认入口，现场可用现有扫码登录流程兜底。
4. C 轮询状态（经 B），拿到会话令牌，完成登录。
5. C 用自己的设备 ID 注册，出现在这个账号的设备列表里。

B 看不到 C 的令牌：C 到官网的 TLS 是端到端的，B 只转发字节。兜底：B 没登录时，C 的仪表盘直接显示二维码，走今天的扫码登录。

**边界**

- 只承载 DNS 和 TCP。UDP 不走搭桥，因为现有通道没有 UDP 载荷。
- B 下线，C 就失去出口。本轮不做网关自动切换；C 的页面明确显示「出口设备离线」，你可以换一台。
- C 加入的是批准人所在的账号，也就是 B 登录的账号。

**已确认（2026-11-25）**：只承载 DNS 和 TCP，UDP 不走搭桥。

**首个端到端验收**：C 只允许访问 B 的局域网地址，B 保持出网。先用预配对端验证 DNS 和 TCP，随后走未登录 C 的首次批准、登录、注册。手机可见 C 在线，并能发起一次实际 AI 回合。分别记录普通 HTTP、深度 TUN 覆盖范围，以及 B 离线、恢复和撤销后的表现。

## 4A. 搭桥入口管理：现状与优化

**现状（已有的）**

- 对端表：设备 ID、局域网地址、host key、是否允许中继（`app/website/src/components/settings/MeshSettings.js:3-9`）。
- 组网密钥对；授权列表是 OpenSSH `authorized_keys` 格式，注释当设备 ID。
- 转发开关，fail-closed：没开就拒绝转发（`inbound/ssh/mesh_inject.go:69-74`）。
- SSH 入口会话台账：列表、踢出、拉黑。
- 局域网发现候选：只读，点选之后仍要手填（`app/http/handlers/mesh_handler.go:61-63`）。
- 出口链路开关和下一跳：开了之后，平台自身流量（登录、扫码、刷新、更新）经下一跳出去（`processor/egress/egress.go:116-152`）。

**今天要手做的，以及缺的**

- 填对端设备 ID 和 host key。
- 把对方的组网公钥贴进自己的授权列表——没有界面，只能改配置。
- 打开转发开关——没有控件。
- agent 到云端的通道不走下一跳；经本机代理的 443 流量不委托。所以没公网的设备即使手选了下一跳，也上不了云。

**优化清单**

| # | 改什么 | 做完之后 |
|---|---|---|
| A | 搭桥请求与批准协议（C → B，局域网内） | 选一台设备、点一下，密钥自动交换、自动钉扎、转发开关自动打开 |
| B | 出口设备页（B 侧）：「允许被搭桥」开关、待批准项、已授权设备（带权限范围、可撤销）、本机指纹 | 谁在经我出网、谁在互访，一目了然，能撤销 |
| C | 下一跳页（C 侧）：可达出口设备列表、一键搭桥、状态（已搭桥 / 出口在线 / 出口离线）、一键入号 | 内网设备三步入网，不碰配置文件 |
| D | 全量出口模式：DNS + 全部 TCP（含 agent 云端通道）经下一跳；到出口设备自身的连接除外，防自环 | 没公网的设备也能上线、能用 AI |
| E | 连接复用：一个节点一条 SSH 连接、多路 channel；发起侧代拨收敛 | 搭桥后不再每条流一次握手 |
| F | 安全约束：搭桥请求入口是独立的局域网面，独立开关、限速、显式批准，不复用代理面；首次接触时显示 B 的指纹 | 不违反不变量 1 和 2 |

**请确认**：六项的范围。

## 5. 出口与路径：只做手动下一跳

- 下一跳由用户在内网设备上手选。路径就是「C → B → B 自己的下一跳或直接出网」。
- 自动规划不做。云端只记录并展示当前拓扑。
- 跳数上限和防环沿用现有机制（`max_hops`、经停链）。
- 语义不变：流量原样交给下一跳，继续上链还是本机出网由下一跳自己决定（不变量 5）。

## 6. 对话直传

**前提**：设备开了「允许对话直传」，且手机与这台设备有可用的直连路径。

**两态**：云端（默认）/ 直传。开了直传，agent 把这台会话的运行帧经直连链路发给手机，不再经云端；云端没有这段历史，这是用户自选。

**三个配套**

- **本地保留**：手机上直连收到的历史消息保存一段时间再覆盖。建议「30 天或 5000 条，先到先覆盖」，数字可调。
- **切回云端时同步**：用户把这台设备切回云端链路时，提示「是否把本地历史同步到云端」。消息都有唯一 ID，按 ID 增量同步，有多少同步多少。
- **断点切换**：直连断了（离开 Wi-Fi、App 进后台）→ 自动切回云端，从断点续上，不丢不重。

**要接受的代价**：直传期间云端不知道有新消息，所以 App 进后台后收不到通知；用量统计和审批审计只留在设备本地。

**两个难点**

- **协议**：今天手机只认云端加工过的事件，不认 agent 的原始帧。agent 要能直接说手机听得懂的契约。这和 SYNC-05（会话游标）、SYNC-10（共享 sync-core）是同一件事，所以对话直传排在这两项之后。
- **加密**：手机侧没有 TLS socket 能力。第一阶段用一次性短票派生密钥做应用层加密，不写原生模块。

**请确认**：两态、本地保留的默认值、切回时是否默认同步。

## 7. 页面规划

- **设备页**：在线状态；当前链路和候选路径；开关——允许组网、允许被其它设备访问、允许对话直传。
- **下一跳页**（搭桥方）：可达出口设备列表、一键搭桥、状态、一键入号、全量出口开关。
- **出口设备页**（被搭桥方）：允许被搭桥、待批准项、已授权设备及权限范围、撤销、本机指纹。
- **拓扑页**（只读）：设备和链路的现状，边上标载体和延迟。
- **流量策略页**：五类流量的默认链路，可按设备加例外。
- **诊断**：每条路径的探测结果，和「为什么没用这条路径」的真实原因。

把搭桥入网排在最前，是因为它用的是目前唯一在用的载体（局域网直连），不依赖云端协调，而且是你点名的场景。NET-07 到 NET-11 穿插着做。人日是粗估，N1、N5 最可能上浮。
