## 0. 一页结论

**T3 Code 是什么**：开源的 coding agent 控制面——一个 Node 进程（一个 environment）驱动本机已登录的各家 agent（Claude Code、Codex、Cursor、OpenCode 等），网页、桌面、手机三个端是同一类客户端，共用一套 `client-runtime`。MIT（商标除外），7.7 万 star，自述 50 万+ 用户。

**它为什么强**（可迁移的是内核，不是某个功能）：

1. **意图先落盘、副作用后跑、结果即命令**：一条命令在一个事务里提交「事件 + 投影 + 回执 + 待办」，进程在任何时刻崩溃，状态要么「没发生」，要么「已发生且待办在表里」。
2. **崩溃恢复是「作废旧进程的副作用 + 续跑」而不是重放**，并且带连续崩溃熔断。
3. **身份与路由解耦**：地址只是不可信提示，花凭据之前先核对「你是谁」。
4. **一个 server、多端同类客户端**：订阅带游标、快照有界、重连只有一个所有者。
5. **统一线程模型**：同一个 Thread 被复用六次（子 agent、委派、fork、工作流步骤、跨机器），每次只多打一个来源戳；子 agent 是事件流里的一等记录。
6. **权限只收窄**，并且在「将要发生的事件」上判定；界面按能力位诚实降级。

**对我们意味着什么**：

| 专题 | 差距的真正所在 | 首推借鉴项 |
|---|---|---|
| 设备组网 | T3 强在连接目录与凭据引导，全程**没有 NAT 打洞**；我们自建 mesh 的跨网腿在双进程下全断，而且用组网必须先打开一个局域网无鉴权面 | ① 堵住 56432（安全前置）→ ② 打通 piko 托管中继 → ③ 账号地址目录 + Tailscale 地址当普通路由 |
| agent 编排 | 没有「崩溃后替在途回合说真话」的人：agent 一崩，手机上的回合挂 10 分钟变红、审批卡最长挂 24 小时、CLI 成孤儿 | 启动裁决 + 云端重启感知 + 孤儿进程收口 |
| 手机问答同步 | 数据模型已成立（同一会话全端可见）；用户感知差的第一因是 iOS 挂起后彻底失联，第二因是恢复靠整表重拉 | 原生推送（需先推翻此前两次决定）→ 会话级游标 |
| 多 agent | 不缺子 agent，缺「子 agent 作为有身份、有谱系、可寻址的实体」；控制面后端齐全但没人调用 | 先把单停 / 插话的入口接上（纯接线） |

**总量与排序**：四块合计约 190 人日（单人约 9–10 个月）。「都借鉴」是分季度的事，所以必须排序——见 §5 的三阶段路线图，阶段一第一波约 3 周、15 人日，拿到最显眼的一批改善。

**最紧急的一件事与借鉴无关**：核验把 SSH 入口那个洞的严重度往上调了——开着组网 / SSH 入口时，同网段的人可以经 56432 打到 agent 的 56433，**执行任意命令，并用他自己的账号把你的设备静默换绑**（静态链逐环核对，见 §2.1 的 I1）。建议不管借不借鉴都先修，约 2 人日。

## 1. T3 Code 的工程内核（八条）

| # | 内核 | T3 怎么做 | 对我们的启示 |
|---|---|---|---|
| 1 | 意图与副作用分离 | `Command → Orchestrator`（每线程一把锁，锁内纯决策、无 I/O）`→ EventSink`（事件 + 投影 + 回执 + outbox 单事务）`→ EffectWorker`（副作用的结果作为新命令回灌同一个入口） | 不必照搬事件溯源（它也不是教科书式的：事件 payload 是整实体快照、日志只留 1 天）；要借的是「单事务提交点 + 结果即命令」 |
| 2 | 崩溃恢复不重放 | 进程绑定的副作用启动时直接 retire，可重放的重新入队，再补一条续跑命令；`MAX_RESENDS 3`、`MAX_CONTINUATION_CHAIN 3` | 我们的 agent 已做到「先落盘再起跑」，缺的就是最后这一步裁决 |
| 3 | 确定性身份 + 回执幂等 | run / effect / command 的 ID 都可再计算，同 ID 重放返回原结果 | 子 agent、消息、委派任务都需要确定性 ID，重试才安全 |
| 4 | 身份与路由解耦 | 公开描述符 + 路由只是提示 + 花凭据前核对 | 我们每条到达路径各解一遍身份核验，没有可复用的单一入口 |
| 5 | 一个 server、多端同类客户端 | 共享 client-runtime：supervisor / registry / 状态机 / 缓存 / 命令发送；平台只注入存储、凭据、网络信号、生命周期 | 我们网页（Vue）与手机（RN）是两套实现，但框架无关的逻辑层可以共享 |
| 6 | 统一线程模型 | Thread 复用六次，lineage 戳标来源；父子只走带来源的消息 | 子 agent 要成为一等记录，UI 只读投影 |
| 7 | 权限只收窄 | scope / 模式上限 / link 等级，全链路只降不升；对「计划产生的 events」判定 | 我们设备互访只有「每目标一个布尔开关」 |
| 8 | 能力声明驱动降级 | 编排与界面读 capabilities，不读 provider 名 | 我们有 63 处 Go provider-id 分支 + P / 仪表盘各按名字硬编码 |

**四块之外，T3 真正值得学的是一组工程习惯**：「把本地常驻进程当分布式系统对待」——更新有提交边界与回滚、崩溃有幂等续跑与熔断、日志常开且可离线分析、睡眠 / 电源 / 前台状态都被建模。见 §3。

**两个旁证**：T3 本月出了两场争议——11-23 因中国 fork 事件才补 `TRADEMARK.md`，11-24 遥测读用户 Codex / Claude 凭据文件被扒、当天撤回。许可与遥测上的教训见 §4。

## 2. 四块逐项

每块的格式：我们现状 → T3 怎么做 → 借鉴项 → 明确不借 → 需要你拍板。规模口径：S ≤ 3 人日，M ≤ 2 人周，L 更大。

### 2.1 设备组网（远程接入）

**我们现状**（三仓审计 + 两侧核验）

- 生产里真正承重的只有一条腿：agent 外拨 WSS 到 PhoneServer，所有控制面流量（含手机）经云中继；手机从不直连用户机器。这条腿的韧性机制并不差（唯一重连所有者、ping + 读截止的静默检测、注册门「连上 ≠ 可用」都在）。
- 自建数据面直连四条腿（LAN beacon / LAN 直拨 / piko 中继 / UDP 打洞）内核完成度不低，但跨网两条腿在双进程下 A、B 两侧都断（`ingressfwd` 拼到死口 56442、中继拨号配置只落在 agent 进程、打洞信令 writer 只在 agent 进程），从未在真机承载过流量。核验补充：**所有启动形态都是双进程**（`aliang start` 也会拉起 agent 子进程），这不是某一种部署形态的问题。
- 机器之间最成熟的是 peer_exec（云中继）：同账号 + 目标布尔开关 + 审计；没有按调用方的授权，没有分级。
- **高危未修**：SSH 入口一开，56432 绑到 `0.0.0.0`，成为无鉴权的 SOCKS5 / CONNECT 代理；并且经回环可直达 agent 的 56433——`POST /api/agent/tools/launch`（`tool=command`）可执行任意命令，`POST /api/agent/sync` 直读请求头里的 JWT，可让 agent 以攻击者账号静默换绑。`--host 0.0.0.0` 形态下，同网段任何人还能用自己的账号登录仪表盘并把设备换绑。
- 核验推翻了一条原判：「token 续期后掉线一次」不成立。生产环境 token 到期时间从未落库（`exp` 只来自默认禁用的本地验签），服务端的在线寿命边界整体不生效。真实缺口是「服务端缺 exp 来源」，它同时意味着：**已被官网吊销、但 WS 仍连着的设备没有到期兜底**。

**T3 怎么做**（T3 侧已核验）

- 全程没有 NAT 打洞，也没有局域网发现。跨网靠三种到达方式：Tailscale Serve、SSH 端口转发、T3 Connect（Cloudflare 托管隧道）。
- 好用的内核是四件事：以环境为键的连接目录（多条路由按速度排序）+ 学习路由（通过隧道连上后，把机器当前的局域网 / tailnet 地址学回来，回家自动切局域网）+ 公开「你是谁」描述符（花凭据之前先核对）+ 唯一的重连所有者（回前台 / 切网先探测，不盲目重连）。
- 几条限定（核验补的）：T3 Connect 的数据面是 Cloudflare 边缘，「云不在数据面」只说它自己的 Worker——我们「PhoneServer 签票 + piko 承载」与之同构，差别只在数据面由谁运营。新设备批准默认关、且只管 T3 Connect 路径（T3 默认同样是账号即信任）。私网闸只在 LAN 模式安装。它有 `kind:"mdns"` 路由（把 `<主机名>.local` 当 SSH 远程打开的目标广播），但那不是发现机制。
- T3 的 peer link 拒绝明文 HTTP，要求两台机器数据面可达；我们的 peer_exec 走云中继，两台只要能连 PhoneServer 就行。这反而支持「跨机器委派用 peer_exec，不用 mesh」。

**借鉴项**（合计约 28.5 人日）

| 编号 | 借鉴项 | 借什么 | 规模 | 前置 | 用户得到什么 |
|---|---|---|---|---|---|
| I1 | 统一入口与管理面收敛（安全前置） | 思想 | S · 1.5–2 人日 | 无 | 开组网时同网段的人不能再把这台机器当免费代理，也打不进管理面与 agent |
| I2 | 平台连接韧性：退避阶梯 + 续期不掉线 | 思想 | S · 1–1.5 人日，另加「服务端补 exp 来源」 | 无 | 云端抖动后更快回到在线、不制造重连风暴；被吊销的设备有到期兜底 |
| I3 | 主机侧接入台账与撤销 | 数据模型 | S · 3 人日 | 无 | 电脑上能看到哪些浏览器 / 手机 / 机器连着我，并可一键踢掉 |
| I4 | 中继载体打通：跨网机器互联先走平台托管中继 | 思想 | M · 8 人日 | I1 | 两台不在同一网络的机器之间「平台流量代理」真的能用，诊断页能看出走的哪条腿 |
| I5 | 设备互访分级授权：按调用方授权、可撤销 | 数据模型 | M · 7 人日 | 无 | 可只给「只读」、逐个调用方批准、随时撤销，而不是一个开关对全账号敞开 |
| I6 | 账号地址目录 + 载体抢占 + Tailscale 地址当普通路由 | 数据模型 | M · 7 人日 | I1、I4 | 同账号两台机器不用手填地址就能互见；装了 Tailscale 的用户自动获得跨网直连 |

设计要点：

- **I1** 四道闸：① 代理面来源闸——嗅探结果不是 SSH、来源不是回环、且用户没有用 `--host` 开放局域网代理 → 关闭（SSH 入口的可达面跟 `ssh_ingress` 走，代理面的可达面跟 `--host` 走）；② 代理面回环目标闸——非回环来源的代理连接不得以回环地址为目标（这一道同时封住 56432 → 56433）；③ 管理面远程来源闸——非回环来源访问 `/api/*` 必须带有效仪表盘会话；④ mesh-exit 回环目标闸。
- **I2** agent 侧补「指数退避 + 抖动 + 稳定 30 秒才复位」。P 侧先给 `exp` 建来源（内省接口回 `exp`，或对 JWT 做不验签解码只读 `exp`），`agent.session.refresh` 才有意义；注意 sweeper 一旦生效，会第一次在生产引入「到期即踢」，要一起评估。
- **I4** 最小修复集：`ingressfwd` 目标默认指向 56432；把 piko 中继配置从 agent 推到 core，并在 core 同时注册 `tcp.SetMeshTransportDialSource`（核验发现只做前一半修不通 AI 流改道）；start 形态接 `WireMeshAssemblySeams`；去掉转发端「同设备顶连接」；身份单一真源；roster 假警报。
- **I5** 可简化：`peer.exec` 下发帧已带 `source_device_id`、审计已带 `callerDeviceId`，按调用方授权不需要新身份管线。
- **I6** 两个坑：tailnet 识别不能只看 `100.64.0.0/10`（WARP 与运营商 CGNAT 共用该段），需要补收 IPv6 或由服务端标注类别；并行拨号会叠加 I4 里的「同节点顶连接」，二者互为前提。

**路线：取 C 的排序、B 的骨架**

1. 安全收敛（I1）——不修它，后面任何让 mesh 更可用的改动都是在扩大暴露面。
2. B 的骨架先落地：piko 托管中继（I4）→ 地址目录 + 载体抢占 + tailnet 地址（I6）。
3. 自研 UDP 打洞保留为**按实测数据触发的可选加速**：现有代码与默认开关不动，本轮不做它的跨进程信令桥。

与 2026-11-12 的 Tailscale 形态评估相比，「路线 D（自研打洞）是正解」没有被推翻，只是降级。变了的是：piko 兜底在生产形态下同样不通（「失败恒落 piko」的前提不成立）、打洞率零真机实测、出现了与 SSH 入口的安全耦合、「只识别 tailnet 地址」这条不需要 tsnet 的路线当时没有被单独评估。

**明确不借**：T3 Connect（Clerk 云身份 + Cloudflare Tunnel）、DPoP、配对码 / 二维码引导（我们「账号即配对」更省事）、peer link 走 OAuth 登录对端 `/mcp`、Effect 版 client-runtime 的代码、tsnet 嵌入与 tailscaled sidecar、每条 RPC 声明 scope 的编译期强制表。

**需要你拍板**

- 手机 / 另一台设备在局域网内直连用户机器，与「手机永久只做控制面」（2026-10-29 spec §1.1）冲突。差距分析的默认是**不放开**；要动的话建议先做「明文 + 单用途短票」的仅同网下载实验开关。
- `--host 0.0.0.0` 的语义只剩两个选项：限定为「可信网络」并写进发布说明，或废弃。

### 2.2 agent 编排（AI run 生命周期）

**我们现状**（三仓审计；本专题核验在跑）

- 没有事件溯源式 Orchestrator。编排主体在 agent 进程的内存态单例：每会话同时只允许一个 run，事件带 `run_id` + 单调 `event_seq` 与终态屏障；PhoneServer 是 run 状态的用户面权威，agent 是执行面权威，仪表盘只是视图缓存——三套状态靠帧、订阅快照、双向 kill 对账。
- 三内核三条接入路径（Claude Code headless CLI、Codex app-server、AliangCode 进程内 Go 内核），能力差异没有集中矩阵：Go 里 63 处 provider-id 分支，PhoneServer 与仪表盘各按名字硬编码。
- 韧性做得很厚，历史上几起著名事故（僵尸回合吞插话、续跑不复活、回答消失、会话错位）在当前代码里均已修。
- **最大的结构缺口是「崩溃后没有人在途裁决」**：agent 崩溃 / 重启后，非 Goal 的在途 run 没有诚实终态，只能等 PhoneServer 的 stale sweeper 10 分钟后判 `timed_out`；等审批时崩溃，审批卡最长悬挂 24 小时；三个 AI 启动点在 Windows 上都没挂 Job Object，所以 CLI 成孤儿在两个平台都成立。而最常见的「崩溃」路径恰恰是看门狗直接 `process.Kill()`。
- 跨仓口径冲突：agent 侧刻意取消了墙钟硬顶（默认 0），PhoneServer 侧对非 Goal run 仍有 6 小时 overrun，且不排除工具 / 子 agent 等待。

**借鉴项**（合计约 33.5 人日；自动续跑二期另计约 4.5）

| 编号 | 借鉴项 | 借什么 | 规模 | 前置 | 用户得到什么 |
|---|---|---|---|---|---|
| O1 | 崩溃可恢复：run 收据三态 + 启动裁决 + 云端重启感知 + 孤儿 CLI 收口 | 思想 | M · 9.5 人日（其中云端「重启感知」约 1 人日，可最先上线） | 无 | agent 崩溃或被看门狗重启后，在途回合 60 秒内显示「被中断，可重试」；审批卡不再挂一天；不留还在改文件的幽灵 CLI |
| O1b | 时长口径对齐：关掉云端 6 小时墙钟上限 | 思想 | S · 0.5–1 人日 | 拍板 D7 | 通宵干活的回合不再在第 6 小时被误杀 |
| O2 | 审批策略单决策点 | 思想 | M（偏小）· 4 人日 | 无 | 同一个操作在 Claude、Codex、AliangCode 上审批结果一致 |
| O3 | 本地 / 仪表盘 / MCP 回合纳入同一套 run 收据 | 协议 | S · 3 人日 | O1 的第一步 | 电脑上聊到一半 agent 崩了，回来明确写着「上一回合被中断」并可一键续跑 |
| O4 | kernel 能力矩阵 | 数据模型 | M · 7.5 人日 | 无 | 不支持的操作在界面上是灰的并说明原因；也是跨内核委派的地基 |
| O5 | 排队 follow-up（可选） | 思想 | M · 8.5 人日 | O4 | 电脑上正在跑，手机再发一条排在后面自动执行，而不是报「会话忙」 |

设计要点：

- **O1** 不新建账本，复用 `agent_ai_identity.json` 的 `processed_runs` 收据（Goal 路径已有同款重启裁决）。agent 启动时对在途 run 分类裁决；云端用 hello 里的 boot_id 变化或 agent 运行时长回落来感知重启（60 秒内收敛），不新造握手帧；子进程记录「pid + 启动时间」所有权，启动时清扫（绝不按 argv 推断归属）。一期只做「人点续跑」，自动续跑留给二期且带熔断。
- **O2** 先给三内核录一张「决策金表」做重构前的特征测试，再收敛成一个 `decideApproval`；差分测试守住三处「同构」之下的行为差异。
- **O4** 能力只有一个事实源（agent），经 hello 上报；旧的 capabilities 字符串由它派生；每个字段配一条「声明 vs 现有探测结果」的一致性测试。
- 与手机同步专题的边界：会话内容（游标、持久订阅、幂等键）归同步专题；本专题只管 run 生命周期事实。

**明确不借（至少现在不借）**：完整事件溯源重写、Effect 风格的 generator 工作流、隐藏 git ref 检查点（列为后续候选）、provider 多实例 / 注册表、managed policy 管理面。

**需要你拍板**

- 崩溃后的处置口径：是否接受「在途回合一律判中断 + 人点续跑」？无人值守来源（监听器 / 定时）要不要自动续跑？
- 时长口径怎么对齐：PhoneServer 的 6 小时 overrun 置 0 与 agent 对齐，还是把 agent 的「无进展」判据下沉到 PhoneServer？

### 2.3 手机问答同步

**我们现状**（三仓审计；本专题核验在跑）

- 数据模型上「一个 server、多端看同一线程」已经成立：agent journal 是转录权威，session id 全端一致，网页与手机双向可见、双向续聊；流式、审批、停止、steer、撤回重发全通。
- 用户感知不如 T3 的三个原因，按权重：① iOS 挂起后彻底失联——**零原生推送**；② 恢复靠整表重拉，而不是协议游标，所以会出现「内容新、状态旧」；③ 网页（Vue，约 4300 行的 composable）与手机（RN，约 1.2 万行）是两套独立实现，同一份会话状态有 8 个副本来源，靠逐段对账。
- 最省力的杠杆已经在门口：agent journal 的会话级 `seq` 已经存在，只是被 PhoneServer 的 `AiMessage` 丢掉、手机没用上。
- **「零推送」不是疏漏**：2026-06-30 与 2026-08-04 两次确认过「不走云端推送、App 被杀不弹」「仅做 Android 本地后台通知、不引入 FCM」。要做原生推送，必须先推翻这两次确认。

**T3 怎么做**

- 不是某个同步算法，而是四层叠起来的：事件溯源投影 + 幂等命令回执；shell / thread 两条订阅各带游标，服务端决定「回放还是换快照」；三端共用 client-runtime，平台只注入存储、凭据、网络信号、生命周期；通知走「服务端投影 → 云 relay → APNs / FCM」旁路，App 不需要在线，通知只带标题 / 阶段不带内容。
- 「妙极」的体感主要来自：唯一的连接所有者 + 订阅自动跟随会话（用户感知不到重连）；返回线程秒开再增量追平；回前台先探测；发消息是幂等命令 + 手机持久 outbox（杀 App 不丢不重）。

**借鉴项**（合计约 49 人日）

| 编号 | 借鉴项 | 借什么 | 规模 | 前置 | 用户得到什么 |
|---|---|---|---|---|---|
| S1 | iOS 原生推送（APNs，由 PhoneServer 直发） | 思想 | M · 约 10 人日 | 你先推翻两次既有确认 | iPhone 锁屏或被杀后，审批到达 / 回答完成 / 运行失败都会响，点开直达那条对话 |
| S2 | Android：国内厂商通道为主 + 海外 FCM + 本地通知去重 | 思想 | L · 约 15 人日 + 资质等待（以周计） | S1；通道选型；企业资质 | 国产安卓被系统杀掉也能收到提醒；没有通道的机型明确提示 |
| S3 | 会话游标：透出 journal `seq` + PhoneServer 分配 `session_seq` + 定向追平 | 协议 | L · 约 10.5 人日（切两片） | 先部署 PhoneServer 后部署手机 | 断网 / 锁屏回来，对话接着刚才的样子出现，审批卡该在的在、该没的没 |
| S4 | 规则化持久订阅 + 消息幂等键 | 协议 | M · 约 6 人日 | 无 | 弱网点发送要么到了且只有一条，要么明确失败可重试；电脑上开跑的回合手机不漏开头 |

设计要点：

- **S1** 我们比 T3 有利：PhoneServer 本来就在数据面、是 run 状态的用户面权威，可以直接发推送，不需要 T3 那种云 relay 代发。推送触发统一挂在一个出口，默认只推「审批到达 / 回合完成 / 运行失败」，设备上下线只做本地通知。去重靠「登记 + socket 按 install_id 关联 + WS 回执」，不能靠「有连接就不推」——iOS 挂起后 socket 在服务端看还能活几十秒，那正是最需要推送的窗口。
- **S2** T3 的做法不能照搬：它 Android 只接 FCM，大陆不可用。国内走厂商通道（或聚合服务）+ 海外 FCM；保活长连接只作兜底。资质、类目、配额是硬前提，建议**资质核实的 spike 现在就启动**，工程排最后。
- **S3** 不做事件回放，做「序号 + 最新快照」：转录行沿用 agent journal 已有的会话级 `seq`，控制态修订号 `session_seq` 由 PhoneServer 分配；「回放还是换快照」的决策点放 PhoneServer（只有它常在线、是云端会话状态的单一写入者）。
- **S5** UI 不共享；共享的是框架无关的 TS 逻辑层（帧 reducer、状态机、游标追平、命令幂等）——Vue 用 composable 绑定、RN 用 zustand 绑定。
- 全部借鉴项都**不需要**放开「手机恒走云端控制面」。

**明确不借**：T3 Connect relay 代发推送、FCM-only 的 Android 推送、Effect 生态 client-runtime 的代码、事件日志逐事件回放、T3 完整版手机持久 outbox、Live Activity / push-to-start、wire 裁剪全家桶。

**需要你拍板**（S1 的前置）

- 是否推翻 2026-06-30、2026-08-04 两次「不走云端推送」的确认？
- 通知里是否显示会话标题（默认取首条用户消息，锁屏可见；建议默认固定文案 + 开关）？
- Android 通道走聚合服务还是直连五家（是否接受通知元数据经第三方）？

### 2.4 多 agent

**我们现状**（三仓审计；本专题核验在跑）

- 我们并不缺「子 agent」本身，缺的是「子 agent 作为一个有身份、有谱系、可单独寻址的实体」。只有内置内核 agentcore 有宿主自有派发（统一 `task` 路由器，结构性 depth=1）；Claude 的子 agent 是镜像，Codex 的子任务完全不解析。
- **最疼也最便宜的是控制面断头**：L3 的单停 / 追加指令 / 续跑在 agent 侧有实现、有单测，WS 分发点也接了，但网页、PhoneServer、手机、`aliang mcp` 面没有任何发送方。子 agent 跑飞时只能整回合重来。
- 零隔离：同进程、同工作目录、同环境变量、同审批闭包。审批先于可见：并行派 N 个会退化成 N 张顺序审批卡，后面几个在通过前面板上看不见。
- 没有编排引擎：多 agent 完全由模型即兴、单回合、无状态；多 agent 编排的 gap spec 已立档（R1–R4），零落地。

**T3 怎么做**

- 同一个线程模型被复用六次，每次只多打一个「来源戳」：provider 子 agent 的镜像线程、`delegate_task`、fork / side chat、`create_threads`、工作流步骤线程、跨机器委派。
- 真正让它好用的是四件事：子 agent 是事件流里的一等记录（UI 只读投影，不从工具调用里猜）；身份 ID 全部从原生 id / commandId 确定性派生（重放不重复、崩溃后能对上）；父子之间只走带来源的 wake 消息（「读即确认 + 超时升级为总是唤醒」）；权限只收窄，且是对「计划产生的 events」判定。

**借鉴项**（合计约 77 人日）

| 编号 | 借鉴项 | 借什么 | 规模 | 前置 | 用户得到什么 |
|---|---|---|---|---|---|
| MA-A | L3 控制入口全链接线（网页 + PhoneServer + 手机） | 思想 | S · 3 人日 | 无 | 子 agent 跑飞时可以只停它或给它补一句话 |
| MA-B | 派发与审批可见性修正 | 思想 | S · 2–3 人日 | 需你拍板「派发免卡」 | 并行派 N 个子 agent 不再弹 N 张顺序卡；审批卡写明是谁、为什么 |
| MA-C | 子 agent 一等记录 + lineage + 确定性 ID + 三内核观测补齐 | 数据模型 | M · 9 人日 | 无 | Codex 子任务不再是黑盒；同一次派发在三端是同一个 task_id |
| MA-D | 工作目录隔离 + 并行写冲突缓解 | 思想 | M · 8 人日 | MA-C | 放心让两个会改代码的子 agent 并行，结果各在一棵干净的树里 |

设计要点：

- **MA-A** 照现成的 `ai.steer` 通路接线即可，沿用既有 `ai.subagent.control` 协议，受 `ai_control_enabled` 门控。
- **MA-C** 记录权威在 agent journal，PhoneServer 只留镜像与结构化事件投影，不新建表；agentcore 的 task_id 改为从内核 `tool_use` id 派生，作为三处统一关联键；Claude 沿用原生 id，Codex 用 `collabCallId:agentThreadId`。
- **MA-E1** 交接是「预算化的原文选段」而不是让 agent 写摘要，省略的部分留 id 指针 + 取回方法。
- **MA-F1** 不做事件溯源，用「行式 journal + 幂等键」实现 journaled step；PhoneServer 管决策与状态、agent 管执行与落盘。T3 的语义（持久 wait、失败暂停、ask / signal）用来补充已有 gap spec 的 R1–R4，不重写。
- 跨机器委派的承载是 peer_exec + peer MCP（云中继），不是 mesh；它依赖 I5 的分级授权。
- 我们有两处「T3 没有」的机制不必自惭：审批单卡门与并发闸是我们对上游限额和手机单卡 UX 的取舍，借鉴 T3 的任何一项都要过这两道门。

**明确不借**：Effect 工作流引擎本体与 TypeScript 脚本 DSL、T3 的 `/mcp` OAuth 体系、fork / side chat / merge-back 的线程级实现、`triage/`、客户端给新线程挑机器的 load-balancing、T3「不做服务端子 agent 并发上限」「审批分散在各子线程」的做法。

**需要你拍板**

- balanced 模式下 `task` 派发是否免卡（与 Claude 的 Task 对齐）？
- 并发闸是否从 per run 改为 per 设备？
- 编排引擎的归属：PhoneServer 定决策与状态、agent 定执行与落盘——是否认可？
- 跨机器委派的鉴权：沿用 peer ACL + I5 分级是否足够？

## 7. 可信度说明

- **已核验并吸收**：设备组网专题。我方侧 29 条断言——25 条成立、2 条部分成立、2 条不成立（都已在 §2.1 改正）；T3 侧主干结论成立，5 处措辞补了限定。两个核验员另列出 20 条遗漏事实，其中改变设计的几条（所有形态都是双进程、I4 要同时注册另一条缝、56432 可达 56433、生产缺 exp 来源）已并入 §2.1。
- **同步专题已核验**：头号建议（iOS 推送由云端直发）的前提全部成立。四处订正：iOS 本地通知其实早已启用，去重设计必须覆盖 iOS；T3 的锁屏通知同样带线程标题；journal 的 `seq` 是在云端的 schema 边界被剥掉的。另发现一个现存缺陷：订阅 30 分钟到期退订时不看是否有在跑的回合，长回合会中途断流。
- **尚未经独立核验**：编排（重跑版）与多 agent 两个专题的差距分析。它们由分析员自行回源码核对并附了行号，但没有经过「专门证伪」的第二双眼睛。立项前最该先复核的几条：
  - 编排：三个 AI 启动点在 Windows 上都没挂 Job Object；审批等待中崩溃会让审批卡悬挂 24 小时；正常退出也只停 HTTP、不收尾。
  - 多 agent：`ai.subagent.control` 在三仓与 MCP 面确实没有发送方。
- **方法局限**：全部是只读静态走读，没有跑测试，也没有真机验证。56432 那条链里，「对局域网成为无鉴权代理、可回环打到管理 API」此前有过跨机实证；「可达 56433 执行命令、静默换绑」是这次核验的静态推演，复现请只在受控机器上做。PhoneServer 与 RN 仓的行号按工作区态（含并行会话未提交的改动）。
